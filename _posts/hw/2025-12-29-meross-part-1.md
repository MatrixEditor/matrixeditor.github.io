## First Steps: Initial Recon

Before diving into the technical specifics, it's essential to identify potential entry points for investigation. In this case, there are three key areas:

* frontend: end-user application (mobile app)
* backend: Meross cloud
* applicance: IoT device (smartplug)

I wont explain too much about the architecture here, but [@albertogeniola's protocol introspection](https://albertogeniola.github.io/MerossIot/meross-protocol.html) is a good starting point. In a few words: each *appliance* is bound to a user account with
a <u>shared key</u> generated by the *backend*. All commands transmitted from the frontend are sent over an MQTT broker using the Meross cloud backend, and messages are not end-to-end encrypted; only signed with the shared key (more on this in a bit).

Given there are a lot of places to look and there is already a ton of research on the protocol, like

* [meross-local-control](https://github.com/andrew-schofield/meross-local-control),
* [mss310-kontrol](https://github.com/mrgsts/mss310-kontrol/blob/master/jsonapi.md),
* [meross-iot](https://albertogeniola.github.io/MerossIot),
* among many others...

Some terms used throughout this series:

- **`Uuid`**: a unique identifier for each Meross device (`32` characters)
- **`Mac`**: the device's MAC address (also unique)
- **`BindId`**: an identifier generated by the device used in the MQTT client id (`16` characters)

Terms related to Meross cloud accounts:
- **`UserId`**: unique/running number that idenfies the user account
- **`Token`**: authentication token for the cloud HTTP API (`64` characters)
- **`Key`**: a *shared key* used to sign protocol messages. Both the app and device must know this secret to be able to communicate with each other.

## Findings

<div align="center">
<b><i>[Note - all vulnerabilities have been responsibly shared with Meross in January 2026. Since then (Nov 2026), only two of the findings has been addressed so far]</i></b>
<br>
</div>

To keep a long story short, the following is a list of all privacy and security related issues I came across while diving into the architecture of Meross IoT devices:

1. All messages are **not** encrypted when sent to the cloud (for most devices); only signed with a *shared key* bound to one account. This means that anyone with access to these keys can forge messages (e.g., control other devices), and those accessing the broker will be able to see all messages. (*see Part VI*)
2. The firmware is **not** encrypted and signed with the **default keys**, which makes it possible to create custom firmware. (*see Part IV*) (**not fixed as of Nov. 2026**)
3. During account setup, some private information are shared with Meross (which can be circumvented - *see Part II and III*), including the internal Wifi-MAC, IP-Addresses as well as (update 2025) tracking information of the mobile device used to setup the account. (*see Part II*)
4. There are **no** backdoors when verifying message signatures within the firmware.
5. Stack Buffer Overflow when receiving messages from the cloud (**fixed by Meross in latest releases**)
6. Message signing in the local network is meaningless when a device does not support message encryption (**not fixed as of Nov. 2026**)
7. The UUID of a device is/was enough to transfer ownership to an attacker (**fixed by Meross**)

Overall, without the mobile application (you don't need it), there's only minimal data collection compared to other manufacturers, and using a local MQTT broker might be an alternative (*setup explained in Part III*).
